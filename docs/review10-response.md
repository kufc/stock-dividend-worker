# 第十輪外部審查（39 條）的逐條回覆

審查報告：2026-11-27，第三版（審查端只讀程式碼，沒有執行）。這份文件是開發端的回覆：每一條查證的結果與處理。
「已修」的都有自動測試（主要在 `tests/test_review10.py`、`tests/test_regressions_review9.py`），
Windows 專屬的部分在 Wine 加安裝版內建的 Windows Python 裡跑過。**2026-11-28 起整套測試也在真的 Windows 上跑**（GitHub 的 Windows 執行環境，Windows Server 2025；每次推送自動執行）：預設設定下全部通過，包含用真的資源回收筒的測試。沒有涵蓋的：真模型（那個環境沒裝 torch）、安裝程式、Windows 10／11 家用版、網路磁碟與 OneDrive。
報告的行號對的是原本的 1.1.0 包，修改後已經位移。

## 判讀改善路線（報告第四節）

- 第 0 步（新的獨立測試集）：**已做**（1,342 張圖片＋231 個影片，原始檔、兩可、影片都有；2026-11-27 評測一次，沒有依結果改任何東西）。缺的：人像／寵物／美食的 HEIC、.mov 與 HEVC 影片、帶旋轉旗標的影片。「都不是」占 10%／36%／60% 與 3／5／8 個分類的表已經補上（`docs/evaluation.md`）。
- 第 1 步做法甲：已試，不採用（見上）。做法乙（詞彙當反例）：已在開發集試，同樣檢查量下少收約 4 個百分點，但誤標加倍、而且開發集可能高估，不採用（數字在 `docs/evaluation.md`）。
- 第 2 步（從修正學習）：**已做，只在同一批內**。只會多提醒、不自動改分類。模擬的上限：開發集未知誤接受 34.8% → 27.1%；第二份獨立測試集（做法定案後才收集）圖片 25.6% → 11.8%、影片 34.4% → 23.4%（標準模型），代價是多看約 6% 的檔案。細節見 `docs/evaluation.md`。
- 第 3 步：影片的三項（切方塊／補邊、丟黑畫面、逐格判斷都不是）都處理了——黑畫面已修，另外兩項在影片開發資料上試過不採用；壞圖進需檢查（A9）已修；直式影片轉正（A10）補了測試；自訂分類的描述（A3）量過、改了說明文字。
- 第 4 步（換模型或加第二個模型）：**做了可行性試驗，不採用**。多語言的 SigLIP 2（B/16）第一名分對 98.2%（現行 97.5%，在誤差內），判斷「都不是」沒有比較好，「每類各自給分」反而比較差；「兩個模型意見不同就檢查」等於把門檻調高一點。數字在 `docs/evaluation.md`。
- 影片的兩個弱點（合照被當成人像、被分成迷因梗圖）：在影片開發資料上試了四種合併方式和一條合照規則，最好的只多對 1.9 個百分點，沒到條件，不採用。

## 這一輪另外發現的事

- 分類少（3～8 個）時，開發集上有一半左右的檔案會進「需檢查」，未知內容仍有三成被接受。這個使用情境之前沒有量過。
- 用 Wine 跑含有多個視窗測試的檔案時，偶爾有測試在建立視窗時失敗，重跑就過。錯誤訊息顯示 Tcl 找到啟動檔卻讀不出來、錯誤碼是「Success」，看起來是 Wine 讀檔的偶發問題（推論）。
- 第一次在 Wine 下跑**整套**測試，找到一個程式的小問題：移除原檔／復原的確認視窗把資料夾路徑顯示成全小寫（紀錄裡存的是比對用的形式）。已改成顯示磁碟上真正的寫法。
