## A. 審查的 P2

### A1. 影片：依長度與場景取樣（審查第 7 項）

**現況**（`media_sorter/media.py` 的 `sample_video_frames`）：不論片長都平均取 8 張（最多 32）。
兩小時的影片和十秒的影片看的張數一樣；無法跳轉的檔案會從頭解碼到尾，沒有時間上限。
獨立測試集裡**沒有影片**，所以影片的準確度目前沒有數字。

**設計方向**

- 兩種模式：「快速」維持現在的做法；「深入」依片長決定張數（例如每 N 秒一張，設上下限），
  再用相鄰畫格向量的差異找場景切換，每個場景至少一張。
- 每張取樣畫面保留時間戳，結果從「整支影片一個分類」擴充成「哪幾段像什麼」；檢查頁可以顯示幾張代表畫面。
- 每個檔案的預算：解碼時間、畫格數、記憶體。超過就用已經拿到的畫面，並標註「只看了前面一部分」。
- 語音轉文字、畫面 OCR 屬於 B2，不放在這一項。

**會動到**：`media.py`（取樣與預算）、`analysis.py`（`Item.frames` 要帶時間戳、`PREPROCESS_VERSION` 加一讓舊結果重算）、
`workdb.py`（frames 的格式；`video_frames` 這個鍵要換成取樣設定的描述）、`config.py`／設定視窗（模式選項）、
`views.py`（代表畫面）。

**風險**：深入模式會慢很多（長影片可能數十倍），需要進度與取消；場景偵測的門檻需要有標記的影片來定，
而目前沒有影片評測集——**應該先收集影片測試集再做**，否則無法知道有沒有變好。
無法跳轉的格式（部分 AVI、直播錄影）仍然只能循序解碼。

**驗收**：一份有時間標記的影片測試集（短片、長片、多場景）；量「漏掉的事件比例」與每支影片的處理時間；
單一檔案不超過預算。

### A2. 多標籤資料模型（審查第 8 項）

**現況**：一個檔案只有一個最終分類（`Item.chosen` 或第一名），整理＝複製到一個資料夾。
「女兒在東京吃拉麵」只能選一個。

**設計方向**：把四件事分開——媒體本身、標籤（多個，含來源：AI／人工）、人物與事件、實體輸出位置。
資料夾整理變成「依某個規則輸出」的功能之一（例如「以這幾個標籤的優先順序決定資料夾」）。
工作資料庫（`workdb.py`）已經是 SQLite，加 `tags(path_key, tag, source, score)` 表是自然的延伸。

**會動到**：這是最大的一項。`analysis.py`（`Item` 的狀態模型）、`workdb.py`（schema 2 與遷移）、
`app.py`／`views.py`（檢查頁從「選一個」變成「勾幾個」；左側的分類清單要能表達交集）、
`organizer.py` 的 `plan_operations`（一個檔案對一個目的地的假設）、整理紀錄的格式。

**風險**：介面複雜度上升很多，現在「一個分類一個分類看縮圖」的流程是這個程式好用的原因；
多標籤的自動判斷需要「每個標籤各自成立與否」的門檻，而現在的分數是分類之間的相對值（softmax），
不能直接拿來用——要改用每個標籤對「其他東西」的二元比較（這一輪替「分類少於 3 個」做的計分就是這個形式，
可以沿用），而且每個標籤都要重新評測。「複製到多個資料夾」會讓「只複製、原檔不動；移除原檔另外確認」的保證
需要重新定義（原檔對應多份複本時，哪一份算「留下的那一份」）。

**建議**：先做「一個主要分類＋多個標籤（只用來搜尋與篩選，不影響複製到哪裡）」，檔案安全的模型完全不用動。

### A3. 重複檔與相關檔案配對（審查第 9 項）

**現況**：只有撞名防護。完全相同的檔案會被各自分類、各自複製；Live Photo（HEIC＋MOV）、RAW＋JPEG、
XMP sidecar 會被當成獨立的檔案，可能被分到不同資料夾，RAW 與 XMP 則根本不在支援的副檔名裡（不會被複製）。

**設計方向**（照審查的兩層）

1. **完全相同**：先比大小，大小相同才算內容雜湊（複製時已經在算 BLAKE2b，可以存進工作資料庫）。
   在檢查頁列出「這幾個檔案內容完全一樣」，預設只整理其中一個、其餘標示為重複；**不自動刪除任何東西**。
2. **視覺相似**：用已經有的向量找候選（同一批內的最近鄰），只當成「請你看一下」的清單。
   視覺相似不等於可以刪：連拍、修圖前後、不同解析度都會很像。
3. **配對**：同資料夾、同主檔名、時間相近的 HEIC＋MOV、RAW＋JPEG、任何檔＋`.xmp`／`.aae` 視為一組，
   分類跟著「主要」的那個走，整理時一起複製到同一個資料夾，移除原檔時整組一起確認。

**會動到**：`config.py`（RAW 與 sidecar 的副檔名；RAW 需要解碼器或只當附屬檔處理）、`media.py`（掃描時配對）、
`analysis.py`（群組的概念）、`workdb.py`（內容雜湊、群組）、`organizer.py`（一組檔案的計畫與紀錄；
`_validate_row` 目前要求副檔名是圖片或影片）、檢查頁。

**風險**：這一項直接碰到檔案安全。「重複所以不複製」如果判斷錯，使用者以為有備份其實沒有——所以第一版應該
**照樣複製每一個檔案**，只是標示出來。配對規則猜錯會把不相干的檔案綁在一起；sidecar 沒有跟著走則會讓修圖設定遺失。
移除原檔的「另一份內容相同的檔案必須存在」必須對組裡的每個檔案各自成立。

**驗收**：人工建立的重複／連拍／Live Photo／RAW 組合；任何情況下原檔集合的每個檔案都至少還有一份內容相同的複本。

## B. 審查第五節之後的產品方向

### B1. 自然語言搜尋

**設計方向**：向量已經存在工作資料庫裡（`files.embedding`）。搜尋＝把查詢文字轉成向量、跟所有檔案的向量算內積、
排序。十萬個檔案的 512 維內積是毫秒等級，不需要向量資料庫。需要一個常駐的「媒體庫」概念
（目前是每次選一個資料夾辨識），以及搜尋結果的介面。

**會動到**：`workdb.py`（依資料夾讀出全部向量）、`classifier.py`（只載入文字端即可回答查詢，可以更快啟動）、
新的搜尋頁。

**風險**：這是「從整理工具變成媒體庫」的方向性改變（Immich、PhotoPrism 的定位）。搜尋的品質沒有評測集。
索引只涵蓋辨識過的資料夾，使用者會期待它知道所有照片。

### B2. OCR、語音轉文字

**設計方向**：選用的額外模型，結果存成每個檔案的文字欄位，併入搜尋與「文件收據／螢幕截圖」的判斷。
**風險**：又一個數百 MB 到數 GB 的下載、又一組固定版本與評測；繁體中文 OCR 的品質要實測；
處理時間明顯增加。離線政策（`netpolicy`）要涵蓋新模型。

### B3. 英文介面與訊息資源化

**現況**：所有介面文字是寫在程式裡的繁體中文字串（`app.py`、`views.py`、`dialogs.py`、錯誤訊息），
`tests/test_docs.py` 用字串比對檢查文件與程式用語一致，安裝程式已經有中英兩種語言。
**設計方向**：字串表（鍵 → 各語言），介面與錯誤訊息都從表裡取；預設分類的名稱與描述也要有英文版
（這會是另一組需要評測的分類）。
**風險**：改動面非常廣（幾乎每個檔案）、容易出現漏翻或版面跑掉；很多測試用中文字串斷言。
建議等功能穩定後再做，而且一次做完。

### B4. ONNX Runtime／Windows ML

**動機**：PyTorch 是安裝體積（數 GB）與安裝失敗的最大來源；ONNX Runtime 加 DirectML 可以支援
AMD／Intel 顯示卡，安裝小很多。
**設計方向**：把兩個模型匯出成 ONNX（影像端、文字端），`classifier.py` 抽出後端介面。
**風險**：匯出的模型要逐一驗證向量與 PyTorch 版本一致（`tests/manual` 的向量檔可以當基準）；
fp16、不同執行提供者的數值差異會影響門檻；DirectML 的相容性只能在真的 Windows 與各家顯示卡上測。
這個環境沒有 Windows 也沒有顯示卡，**無法在這裡驗證**。

### B5. 換模型（例如 SigLIP 2）

**現在可以做的**：評測流程已經有了——對候選模型跑 `tests/manual/dump_embeddings.py`（開發集）選設定，
最後在獨立測試集報告一次。
**注意**：(1) 獨立測試集每多用一次就少一點獨立性；比較多個候選模型請用開發集，只有最後入選的才上獨立測試集，
或另外再收集一份。(2) 這一輪的結果顯示高精準模型（ViT-H）在獨立測試集上沒有比標準模型（ViT-B）好，
所以「模型越大越準」在這個任務上不成立，換模型前先確認要解決的是哪個數字（很可能是未知類別誤接受率，而不是封閉正確率）。

### B6. Metadata 匯出（XMP／IPTC）

把分類寫成標準的 metadata（digiKam 的做法），整理成果就不綁在這個程式上。
**風險**：寫入 metadata 等於修改檔案——跟「原檔不動」的底線衝突。只能寫到複本，或寫成 sidecar（`.xmp`）。

### B7. 發行：簽章、SBOM、更新

- **簽章**：流程已經有（`installer/sign.py`、`build_installer.py --sign`），缺的是憑證。這需要你決定與付費。
- **SBOM**：`requirements.lock` 加上 `RUNTIME-PACKAGES.txt`（conda 套件清單）已經是完整的清單，
  轉成 CycloneDX 格式是小工作。conda-forge 的內建 Python 目前**沒有**固定到確切的 build（只固定 3.12.*）。
- **有回復能力的更新**：目前升級＝重新執行安裝程式。要做自動更新需要簽章先到位。

| 人工修正時間等指標 | 審查建議量「人工修正時間」「不同語言、裝置、來源的成績」 | 需要真人操作與另外的資料，沒有做 |

## D. 建議順序

1. **先處理未知內容誤接受率**（C 的第一項）。它不需要新功能，直接影響每個使用者，而且評測流程已經就緒。
2. **在真的 Windows 上驗證並取得簽章**（C、B7）。這是公開發行的前提，跟功能無關。
3. **A3 的第一層（完全相同的檔案）與配對**。使用者馬上有感、設計單純；視覺相似留到後面。
4. **A1 影片**——先收集影片測試集，再改取樣。
5. **B1 搜尋**與 **A2 的精簡版（主要分類＋標籤）**。這兩項一起決定產品要不要從「整理工具」走向「媒體庫」。
6. **B4 ONNX**、**B3 英文介面**：投入大、需要真機，放在方向確定之後。
7. **B2 OCR**、**B5 換模型**、**B6 metadata**：依需求。

## E. 需要你決定的問題

1. 產品定位：維持「把資料夾整理好就結束」的工具，還是走向常駐的媒體庫（搜尋、標籤、重複檔審查）？
   A2、B1 做不做、做多大，取決於這個答案。
2. 未知內容：你比較能接受「多看一些需檢查的檔案」，還是「少看、但分類資料夾裡會混進別的東西」？
   這決定預設門檻往哪邊調。
3. 「自動」模型要不要改成一律用標準模型？
4. 要不要投資程式碼簽章憑證？沒有它，安裝程式的警告就會一直在。
5. 要不要正式支援 Windows 以外的系統？
6. 原檔在網路磁碟上時：維持「不移除」，還是提供同磁碟的隔離資料夾？
