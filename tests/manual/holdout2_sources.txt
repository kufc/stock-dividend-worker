HOLD-OUT SET No. 2 ("holdout2") - DO NOT USE FOR TUNING.
This set was collected on 2026-11-27, AFTER all default prompts, thresholds and rules were fixed. It replaces the
first hold-out set (holdout_sources.txt), which is "used up": a threshold decision was influenced by it. Never tune
prompts, thresholds or rules against holdout2; if that ever happens it is no longer a hold-out set and a new one has
to be collected. Every evaluation run on it has to be written into the evaluation log in docs/evaluation.md.
The person who collected it only collected, labelled and embedded: the classifier was never run on any file before
the selection and the labels were final, and no accuracy number was computed while collecting.

Files behind
    embeddings_holdout2_standard.npz / embeddings_holdout2_accurate.npz              1,342 images, 44 folders
    embeddings_holdout2_video_standard.npz / embeddings_holdout2_video_accurate.npz    231 videos, 27 folders
All files come from public, non-gated datasets on the Hugging Face Hub (46 dataset repos). None of the datasets of
the dev set (photo_sources.txt) or of the first hold-out (holdout_sources.txt) is used, nor any repackaging of the
same underlying data. The images / videos themselves are NOT committed (licences differ); they are rebuilt by
    python tests/manual/collect_holdout2.py --out <dir>          ->  <dir>/images/<group>/...  <dir>/videos/<group>/...
which pins every dataset to a commit hash (REV in the script). <dir>/images/manifest.tsv and <dir>/videos/manifest.tsv
list: final group, file, the group the file was picked for, source key (dataset:file#row), kept / moved / removed.
(Checked: a second build from the script's download cache reproduces all files and both manifests byte for byte.
A build from an empty cache was not repeated.)
The embeddings were made with
    python tests/manual/dump_embeddings.py --preset <standard|accurate> --only-extra --per-class 0 --keep-original
        --extra-dir <dir>/images --out tests/manual/embeddings_holdout2_<preset>.npz
    (and --extra-dir <dir>/videos --out tests/manual/embeddings_holdout2_video_<preset>.npz)

What is different from the first hold-out
1. ORIGINAL FILES. Every file is stored with the bytes and the extension the dataset gives it - no re-encoding, no
   resizing - and goes through the app's real loaders (EXIF transpose, transparency -> white, HEIC, video frame
   sampling, pixel limit). The first hold-out re-saved everything as JPEG <= 1024 px, so those paths were never
   measured. In the .npz the n-th file of a folder (sorted by name) is x_<group>_<n><original extension>;
   image_sources holds "<group>/<file name>", failed_* list the files the loaders could not read (none are dropped
   silently).
2. AMBIGUOUS FILES ARE KEPT. A file that is genuinely between two default categories sits in a folder named with both
   labels joined by "+" (order = order of the default category list), e.g. 人像+風景; image_labels is that name and
   either answer is to be counted as correct. 99 images and 33 videos are labelled this way.
3. VIDEOS. A separate video set (231 short clips).
4. Unknown ("none_*") content is of different KINDS than in the two earlier sets.

Selection discipline
- Every pick is random with a fixed seed, random.Random("20261127:<group>:<source>"), using only dataset labels and
  metadata: folder names, file names, class labels, captions, hashtags, EXIF tags (rules below).
- Then every folder was looked at on contact sheets (200-px thumbnails; unclear files were enlarged; videos: 3-4
  frames each). The label of a file follows what the file SHOWS:
    * kept   - the metadata label is right;
    * moved  - the metadata label is wrong or incomplete: the file goes to the folder it really belongs to
               (a default category, a "+" pair, or a none_ group) and is called <picked-for group>_<NNN><ext>;
    * removed- only if it is unrecognisable, or sits between "no default category" and a default category
               (the first hold-out deleted those too; "+" folders are only for two DEFAULT categories), or
               between three categories.
  Nothing was removed or moved for looking "hard": tiny subjects, dark, blurred, sideways, low-resolution files and
  near-duplicates stay. All by-eye decisions are the REMOVED_* / MOVED_* lists in collect_holdout2.py.
- Rules of thumb used for the "+" folders: a person / people AND scenery, a building, a vehicle, plants, food or an
  animal, where neither clearly dominates (typically the person takes well under half of the frame height, or is
  seen from behind in front of a sight); a street scene where parked or passing vehicles are as prominent as the
  buildings; scenery with a prominent boat / aircraft wing; cartoon art with a meme caption, or a caption-less
  cartoon sticker from a meme collection (動漫插畫+迷因梗圖); every file of a cat-meme collection (貓+迷因梗圖).
- Changes made to the selection after seeing contact sheets (all before any model was run, all on metadata only,
  none aimed at difficulty):
  * 合照: Conceptual Captions gave only 22 hits in its whole validation split, so 50 photos of personal event albums
    (CUFED) were added; that source has no per-photo label and is labelled by eye.
  * 美食 / 交通工具 / 迷因梗圖 fell below 50 after the review (many travel photos picked by caption turned out to be
    scenery or street views; many Chinese stickers are cartoon stickers) and were topped up from the same or a
    sibling shard: +8 Vietnamese dishes, +10 Stanford Cars and +9 FGVC-Aircraft, +14 Hateful-Memes (train split).
    The new files are numbered after the old ones; none of them was removed.
  * EXIF orientation: the random picks contained almost no file with an Orientation tag other than 1 outside
    none_banknote, so one source was added that takes EVERY file with Orientation 3 / 6 / 8 of three CC0 repos of
    unlabelled Japanese snapshots (19 files, labelled by eye; see none_snapshot).
"License" is what the dataset card's license tag states; "not stated" = the card has no license tag.

== Not found / skipped ==
- HEIC is only present as still photos of two kinds (campus buildings, books). No public HEIC source for people,
  pets or food was found; nothing was converted to HEIC.
- EXIF-rotated originals of people, pets, food are rare in public datasets (most are re-encoded): only the files
  listed above.
- Videos for 螢幕截圖 / 文件收據 / 動漫插畫 / 迷因梗圖 (screen recordings etc.): no labelled source was looked for
  further; a few TikTok clips with meme captions ended up in "+" folders.
- No .mov, no rotation-flagged and no HEVC video. Video total download ~555 MB, images ~1.0 GB.
- Tried and rejected before any file was selected: google/docci (loader script fetching from another host),
  useKled/* (gated), AbhinayGampa/family-photos-fullres and trentmkelly/tea-app-selfies (private-looking personal
  photos), visheratin/google_landmarks_photos and the Pexels / Unsplash sets (URL lists; hosts other than
  huggingface.co are not reachable), EmileEsmaili/sheet_music_clean (printed pages - too close to 文件收據),
  pixel-art sets (too close to 動漫插畫), flwrlabs/celeba (not needed after FairFace).

== Known limits and debatable labels ==
- Heavy by-eye labelling. Three sources have no usable per-file label and are labelled entirely by eye
  (Scenery_of_japan, CUFED, the EXIF-rotated snapshots), and the caption / hashtag rules (xhs, TikTok, Mixkit titles)
  were corrected by eye in a large share of cases (e.g. xhs "vehicle": 2 of 22 kept). One reviewer, mostly on 200-px
  thumbnails. For these sources the expected label is the reviewer's judgement, not a dataset label.
- The "+" decision (person vs. scenery etc.) is a judgement call; borderline files were put INTO a "+" folder rather
  than into a single category. A stricter or looser reviewer would move maybe 20-30 files either way.
- none groups that can be argued about: none_sports and none_music videos show people (a user might accept 人像 /
  合照; three music clips are close-ups of one singer); none_banknote shows a printed portrait; none_book shows
  printed covers (close to 文件收據?) and some covers carry drawings; none_gadget includes laptops with a visible
  desktop and water bottles (a drink?); none_cards are synthetic composites on texture photos (one on a waffle, one
  on a drawn face); none_parrot are pets, but not cats / dogs; none_snapshot contains a coral and a squirrel;
  none_misc videos include guinea pigs with their owner and lizards.
- Train interiors, railway tracks, bus-stop displays, hot-air balloons (video), factory chimneys, temple and hotel
  interiors were REMOVED or put into none_snapshot depending on how clearly "nothing" they are; a user could file
  some of them under 交通工具 or 城市建築.
- Packaged food and drinks: packaged snacks, instant-noodle packs on a shelf, drink cans and one sake bottle are
  美食; tea tins and liquor bottles in a wall niche were removed. This line is thin.
- 人像: three very different kinds - travel portraits (young women, full body, scenic background), 224-px face
  crops, cut-outs on transparency, stock portraits. 合照: includes couples, candid party / wedding photos (dark,
  blurred) and crowds.
- 貓 / 狗 images are clear single-animal photos (an easy set); the cat and dog VIDEOS are harder (owners in frame).
- 風景: travel-poster-like xhs photos plus dull sky / snow snapshots, with near-duplicate series (cloud photos,
  snowy woods). 城市建築: one US campus (24), Asian temples and streets, blurred Japanese night views.
- 花草植物 has trees and street greenery from Taiwan next to studio-like flower close-ups.
- 螢幕截圖 / 文件收據: clean sources, nothing was removed; no chat screenshots, no ID cards, no Chinese receipts.
- 動漫插畫: Japanese-style only; 22 of 63 are posters with lettering. 迷因梗圖: English image macros (some
  offensive) and 12 Chinese ones.
- Xiaohongshu photos are WebP data in files called .jpg, and the faces in TaiwanVQA are sometimes greyed out by the
  dataset authors.
- The video set is small (11-24 per folder): per-folder numbers will be very noisy. Stock footage (Mixkit) is
  cleaner than what people shoot themselves; the TikTok clips are closer to a real phone folder but have captions,
  effects and cuts.
- tools/evaluate.py (Recorded.items) currently treats only names ending in ".mp4" as videos; the 22 ".avi" clips
  have their frame vectors in frame_owner / frame_emb like every other video, but that loader would score them from
  the combined vector unless it is extended to the other video extensions.
